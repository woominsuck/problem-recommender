# 문제 은행 추천 엔진

질문 네 개 이내로 문제 은행을 좁혀, 지금 나에게 맞는 문항 다섯 개를 추천하는 웹 서비스입니다.
고급수학 기출 114문항, 개념 태그 177개로 구성되어 있습니다.

## 해결한 문제

시험 기간에 기출을 풀 때 문제를 **푸는 시간보다 고르는 시간이 더 길어지는** 상황이 반복됐습니다.
태그로 직접 걸러 보면 단원 7종 × 유형 5종 × 난이도 5단계 × 개념 태그 177개라 조합이 폭발하고,
조건을 조금만 좁히면 결과가 0개가 됩니다. 반대로 설문처럼 20개를 물으면 아무도 끝까지 답하지 않습니다.

그래서 **적은 질문으로 최대한 좁히는 것**을 알고리즘 문제로 풀었습니다.

## 사용한 알고리즘

| 단계 | 알고리즘 | 역할 |
|---|---|---|
| 1. 적응적 질문 | 엔트로피 + 목표 대역 비용 | 질문 네 개 이내로 후보를 8개 대역에 안착시킨다 |
| 2. 순위화 | TF-IDF + 코사인 유사도 | 질의 벡터와의 각도로 적합도를 잰다 |
| 3. 다양화 | MMR | 이미 뽑은 문항과 닮은 것에 벌점을 준다 |
| 4. 개인화 | Rocchio 관련성 피드백 | 사용자 반응만큼 질의 벡터를 옮긴다 |

### 질문 선택 기준을 바꾼 이유

정보 이득만 최대화하면 값의 종류가 많은 속성이 항상 이깁니다. 이 은행에서 소단원은 81종이라
정보 이득이 6.21 bit로 압도적이어서, 선택지 81개짜리 질문 하나로 끝나 버렸습니다.
C4.5의 이득비도 여기서는 쓸 수 없습니다. 후보 집합의 엔트로피를 균등분포로 두면

```
IG = log2|S| − Σ p_v·log2|S_v| = −Σ p_v·log2 p_v = H(split)
```

이므로 이득비가 항등적으로 1이 됩니다(실측 1.0000). 그래서 목표 자체를 바꿨습니다.
불확실성을 0으로 만드는 것이 아니라 후보를 8개 대역에 앉히는 것을 목표로 두고,

```
cost(q) = Σ p_v · | log2|S_v| − log2 8 |
```

를 최소화합니다. 후보를 너무 많이 남기는 질문과 1개까지 깎는 질문이 함께 벌점을 받습니다.

### 좁히기 질문과 개념 질문의 분리

모든 질문이 후보를 자르게 두면 후보가 8 → 2 → 1로 무너져 순위화와 다양화가 할 일을 잃습니다.
그래서 두 종류로 나눴습니다.

- **좁히기 질문** — 후보 집합을 자른다 (엔트로피를 줄인다)
- **개념 질문** — 질의 벡터에 개념어만 더한다 (후보는 그대로 두고 순위를 가른다)

## 실행 방법

### 로컬에서 보기

`index.html`을 브라우저로 열면 바로 동작합니다. 인터넷 연결이 없어도 됩니다(웹폰트만 시스템 폰트로 대체).

서비스 워커까지 확인하려면 간단한 서버를 띄우세요.

```bash
python3 -m http.server 8000
# http://localhost:8000 접속
```

### 배포

정적 호스팅에 폴더를 그대로 올리면 됩니다. 빌드 과정이 없습니다.

**GitHub Pages** — 저장소에 폴더 내용을 업로드하고, Settings → Pages에서 Source를 `main` 브랜치 루트로 지정합니다.
`.nojekyll` 파일이 포함되어 있어 `assets/` 폴더가 그대로 서비스됩니다.

**Netlify / Vercel** — 폴더를 끌어다 놓거나 저장소를 연결합니다. 빌드 명령은 비워 두고 공개 디렉터리만 루트로 지정합니다.

## 파일 구조

```
├── index.html              화면 마크업, 메타 태그
├── assets/
│   ├── style.css           스타일
│   ├── data.js             문제 은행 114문항
│   ├── algorithm.js        TF-IDF · 정보 이득 · MMR · Rocchio
│   └── app.js              화면 전환, 계기판, 결과 렌더링
├── manifest.webmanifest    홈 화면에 추가할 때 쓰는 정보
├── sw.js                   서비스 워커 (오프라인 캐시)
├── icon.svg                파비콘 겸 앱 아이콘
├── 404.html                없는 주소 처리
└── .nojekyll               GitHub Pages가 폴더를 그대로 서비스하도록
```

## 다른 과목으로 바꾸기

`assets/data.js`의 `RAW` 배열만 교체하면 됩니다. 알고리즘은 손댈 필요가 없습니다.

```js
// [id, 단원, 소단원, 개념태그[], 유형, 난이도(1~5), 예상시간(분), 본문]
["AM-101", "미분법", "음함수 미분", ["음함수미분","접선"], "계산", 2, 6,
 "곡선 x³ + y³ = 6xy 위의 점 (3, 3)에서 접선의 방정식을 구하시오."]
```

개념 태그는 이름을 일관되게 쓰는 것이 중요합니다. 같은 개념을 다른 이름으로 적으면
문서빈도가 나뉘어 IDF가 흐트러집니다.

## 알고리즘 내부 보기

화면 오른쪽 위 **내부 보기** 버튼을 누르면 다음을 확인할 수 있습니다.

- 질의 벡터의 성분과 크기
- IDF 적용을 끄고 순위가 어떻게 바뀌는지 비교
- MMR의 λ를 조절해 다양성 정도 조정
- 질문마다 몇 bit를 얻었는지 기록한 엔트로피 추적표
- 질문 후보별 목표 이탈 비용 비교표

## 알려진 한계

- 태그를 손으로 달았습니다. 자동 추출과 검수로 바꾸는 것이 다음 과제입니다.
- 태그 177개 중 112개가 문항 하나에만 붙어 있습니다. 300~500문항 규모가 되어야 IDF가 제대로 힘을 받습니다.
- 피드백을 한 사람 것만 사용합니다. 사용자가 늘면 협업 필터링을 얹을 수 있습니다.
- 난이도를 직접 1~5로 매겼기 때문에 주관적입니다. 실제 풀이 시간으로 보정할 필요가 있습니다.

## 수록 문항에 대하여

문항 114개는 모두 직접 작성했습니다. 교재의 문제를 그대로 옮기지 않았습니다.
